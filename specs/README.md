# The `specs/` directory

This directory holds the machine-readable side of the CloudOptix specification
format: the JSON Schema that defines it, a fully-populated reference
instance, and four worked examples across different estate shapes. It is the
artifact-format counterpart to [`docs/onboarding-spec.md`](../docs/onboarding-spec.md)
(SPEC-ONB-001..006), which covers how a file in this shape actually gets
produced — normally nobody hand-writes a `cloudoptix.yaml` end to end. This
document is about the format itself: what it is, how a version is created,
diffed and approved, and how to validate a candidate document against it.

## Contents

| Path | What it is |
|---|---|
| [`cloudoptix.schema.json`](cloudoptix.schema.json) | JSON Schema (draft 2020-12) for the `cloudoptix.yaml` file format, generated by transcription from `internal/domain/spec/spec.go`'s Go struct and its `yaml` tags. |
| [`v1/cloudoptix.yaml`](v1/cloudoptix.yaml) | A fully-populated reference specification using every field the schema defines, for the checkout-api example used throughout the root README. |
| [`examples/`](examples/) | Four complete, schema-valid worked specifications across different estate shapes — see below. |

## What this format is, and isn't

A `cloudoptix.yaml` file is the **customer-facing serialization** of
`spec.Spec` (`internal/domain/spec/spec.go`). It is what a tenant admin
reviews, edits, commits to their own version control if they choose to, and
approves. It is not the same shape as the API wire format `spec.Spec` also
carries (`json` tags) — the two differ in exactly one respect that matters:
`Spec.Provenance` (the flattened per-field provenance map: which fields were
`CONFIRMED` versus `INFERRED` versus `UNKNOWN`, and why) and
`Spec.OpenQuestions` (the agent's outstanding questions) both carry
`yaml:"-"` in the Go source and are deliberately absent from this schema and
from every file in this directory. That information exists — the onboarding
review UI and `GET /specs/{id}` both surface it — but it does not belong in
the file a customer commits to git, because provenance is a fact about *how
this file was produced*, not part of the specification itself. See
`docs/onboarding-spec.md`, SPEC-ONB-002, for the full reasoning.

Put differently: this schema describes the destination format, not the
production process. A file that validates against `cloudoptix.schema.json`
is a well-formed specification regardless of whether it was produced by a
week of onboarding conversation, hand-edited by a platform engineer, or
written by a documentation author populating worked examples — which is
exactly how the four files in `examples/` were produced.

## The specification lifecycle

A `cloudoptix.yaml` document is one **version** of a specification.
`spec.Version` (`internal/domain/spec/spec.go`) wraps a `Spec` with:

- `Status`: `draft → validating → pending_review → approved | rejected | superseded`. Only `draft` is mutable (`Status.Mutable()`); every other status is terminal — nothing edits an approved version in place.
- `Checksum`: a content hash of the frozen specification.
- `Diff`: the structural diff against the version's parent (see below), empty for a first version.
- `Validation`: the result of `spec.Validate()` — every issue found, each carrying a `core.Severity`.
- `Completeness`: counts of fields by provenance (confirmed / inferred / unknown / needs-confirmation) and a `ReadyForReview` flag.

Only one transition makes a version authoritative: `Version.Approve`. It
requires `StatusPendingReview`, re-runs `spec.Validate()` and refuses over
any blocking issue, and records who took responsibility — `ApprovedBy`,
`ApprovalID`, `ApprovedAt`. This is the same mechanical boundary described in
the root README's AI safety model section, applied to the very first
artifact a tenant produces: a conversation, or a hand-edit, or any other
route to a draft file, can propose anything; only a human calling `Approve`
on a validated, `pending_review` version makes it real.

Once approved, a specification version is frozen. Every downstream engine —
discovery attribution, the cost engine, the optimization rule engine, the
governance policy evaluator — reads from the currently-approved version.
Changing anything requires a **new version** (`POST /specs/revisions`), not
an edit of the approved one. This is why `examples/` and `v1/` in this
directory are static YAML files rather than something a script mutates in
place: each one represents a single frozen version, the same way an approved
tenant specification would sit in the platform's own store.

## Validation

`spec.Validate()` (`internal/domain/spec/validate.go`) performs deterministic,
no-model checks — no field in this list depends on an LLM call, which is why
it can run synchronously as part of `Approve` and give an immediate answer:

- AWS account ID format: `^[0-9]{12}$`
- AWS region format: `^[a-z]{2}(-gov)?-[a-z]+-[0-9]$`
- IAM role ARN format: `^arn:aws[a-z-]*:iam::[0-9]{12}:role/.+$`
- Email format (`Member.email`)
- Maintenance-window start time format: `^([01][0-9]|2[0-3]):[0-5][0-9]$`
- Valid `environment` / `riskTolerance` enum membership
- Presence of an organization name
- Presence of an `externalId` when an AWS account is declared (a missing external ID is a confused-deputy exposure — see `docs/security-spec.md`, SPEC-SEC-002 — and is caught here, before any role verification is attempted)
- `automation.enabled: true` with no `maintenanceWindows` declared is rejected — the platform will not accept an automation-enabled specification with no window to constrain it to. The reasoning is stated directly in `spec.Validate()`'s own doc comment: *"automation enabled with no maintenance window means changes at peak traffic."*

`cloudoptix.schema.json` in this directory enforces a strict superset of the
same **structural** constraints (required fields, enum membership, string
patterns) so that a document can be checked before it ever reaches the
platform's own `spec.Validate()` — a CI pipeline validating a
`cloudoptix.yaml` on every pull request, for instance, uses this JSON Schema
directly. The schema is a close mirror of `spec.Validate()`'s regexes and
enums, not an independent definition of them; where the two could drift, the
Go source in `internal/domain/spec/validate.go` is ground truth and the
schema should be corrected to match it, not the other way around.

### Validating a document locally

```bash
python3 -c "
import json, yaml, jsonschema
schema = json.load(open('specs/cloudoptix.schema.json'))
doc = yaml.safe_load(open('specs/v1/cloudoptix.yaml'))
jsonschema.Draft202012Validator(schema).validate(doc)
print('valid')
"
```

Every file in `v1/` and `examples/` in this directory has been validated
this way; run the same check against a candidate file before proposing it as
a new example or reference.

## Diffing

`spec.Diff(before, after)` (`internal/domain/spec/diff.go`) flattens both
specification versions into dotted field paths and compares values, so a
reordered YAML block produces no diff and a changed field always does — the
comparison is over the parsed structure, not the text. Each `Change` in the
result carries an `Impact` string: plain language explaining the downstream
consequence of the change, because `availabilityTarget: 0.999 → 0.9999`
means nothing to a reviewer unless told it will suppress an entire class of
single-AZ optimization recommendations. `SortChanges` orders a diff by
severity then path, so a reviewer approving a new version sees the
consequential edits first, not an alphabetically-sorted list where a typo
fix in a `description` field sits above a change to `automation.enabled`.

A diff is always computed relative to the specification's immediate parent
version — there is no "diff against arbitrary version" operation, because
the lifecycle is a strict linear chain of versions per tenant, not a graph.

## Approval

`Version.Approve` is described above under "The specification lifecycle." A
few points worth restating because they are easy to get wrong when
integrating with the platform:

- Approval is independent of AWS account connection. A specification can be
  validated and approved purely from conversational input — no AWS account
  needs to exist yet. `docs/runbooks/tenant-onboarding-support.md` documents
  this explicitly because it is a common source of confusion for support
  staff: do not tell a user they need to connect AWS before approving.
- Approval requires `spec.Validate()` to report **no blocking issues** —
  non-blocking issues (lower `core.Severity`) do not prevent approval, but
  remain visible for the reviewer to see.
- Approval is a distinct action from *creating* a new draft version.
  Producing `pending_review` status is what onboarding (or a manual edit
  flow) does; only a human — a `tenant_admin` or `architect` role, per
  `docs/security-spec.md`'s RBAC table — can call `Approve` itself.

## The four worked examples

[`examples/`](examples/) contains four complete specifications, each
validating against `cloudoptix.schema.json`, chosen to be as different from
each other as the format allows rather than variations on one theme:

| File | Estate shape | What it stresses in the format |
|---|---|---|
| [`production-ecommerce.yaml`](examples/production-ecommerce.yaml) | A multi-service retail platform, several business units' worth of workloads under one application, aggressive optimization posture | `business.transactions[]` with several transactions of differing criticality and very different unit economics (a `$0.0074` checkout next to a `$0.00019` search query); a large `automation.autoExecuteActions` list |
| [`regulated-financial-services.yaml`](examples/regulated-financial-services.yaml) | A core-banking ledger platform under SOX/SEC 17a-4 | `automation.enabled: false` outright (not just scoped to non-production); a heavy `governance`/`security` section that is load-bearing rather than boilerplate; `optimization.riskTolerance: low` with a long `excludedActions` list |
| [`serverless-startup.yaml`](examples/serverless-startup.yaml) | A five-person team, one AWS account, no formal governance function | The thinnest legitimately-approved specification the schema allows — several optional sections reduced to their minimum, an explicit `UNKNOWN` field left unresolved, and confirmation that only the top-level `required` set actually has to be populated |
| [`multi-account-enterprise.yaml`](examples/multi-account-enterprise.yaml) | An AWS Organizations estate, nine member accounts across three business units, one shared platform team | `aws.accounts[]` at real scale (nine entries, mixed `environment` and `production` values); `teams[]` with multiple teams whose `owns` lists partition the workload inventory; three business units' worth of `business.transactions[]` with wildly different unit economics (a `$0.0000034` telemetry event next to a `$0.038` dispatch assignment) |

Each example is deliberately internally consistent — cost-per-transaction
targets are set to numbers that are plausible for the transaction volume and
architecture described, account IDs and role ARNs are well-formed but
obviously fictional (the `1xxxxxxxxxxx`–`7xxxxxxxxxxx` account ID ranges and
`*.example` email/company domains are used throughout this repository's
documentation specifically so nothing here resembles a real AWS account or
company), and every cross-reference (a `business.transactions[].workloads[]`
entry names a real `workloads[].name`; a `costSlos[].transaction` names a
real `business.transactions[].name`) actually resolves within its own file.
