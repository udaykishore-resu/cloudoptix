# Observability specification

Covers `SPEC-OPS-001..003` — `internal/infrastructure/{config,telemetry,server}`.

## SPEC-OPS-001 — Layered configuration

`internal/infrastructure/config` builds the platform's typed configuration in the order `defaults → config.yaml → environment variables → command-line flags`, each layer overriding the one before it — chosen because it matches how CloudOptix is actually meant to be deployed: a base `config.yaml` ships with the image (safe defaults, no secrets), an environment-specific overlay is mounted or injected by the orchestrator (a Kubernetes ConfigMap/Secret), and a flag is the most explicit, most temporary override an operator reaches for to override one value for one run without touching either.

Secret-shaped fields use a `Secret` type whose YAML unmarshaller refuses a literal value — a `config.yaml` accidentally containing `database.password: hunter2` fails to load with an explicit error instead of working. The platform's secret-handling invariant is enforced by the type system, not by code review catching it in review.

`Config.Environment` gates behaviour that must never run in production: the development-mode static-token auth issuer, permissive CORS defaults, and verbose error bodies.

## SPEC-OPS-002 — Telemetry

`internal/infrastructure/telemetry` wires OpenTelemetry tracing, Prometheus metrics, and structured logging for the whole platform. The one design decision worth stating: the module proxy available while building this codebase blocks fetching a real OTLP exporter package (`go.opentelemetry.io/otel/exporters/...`). Rather than leaving tracing unimplemented, this package writes its own minimal span exporter that renders finished spans as structured `slog` records — every span is still sampled, batched, and flushed through the real SDK's `BatchSpanProcessor`, and correlates with logs automatically because it *is* a log line. The seam for a real OTLP exporter is exactly one interface (`trace.SpanExporter`, from the SDK); swapping one in once the module proxy is available is a one-line change at `NewTracerProvider`'s call site, not a redesign.

## SPEC-OPS-003 — Graceful lifecycle

`internal/infrastructure/server` wraps `net/http.Server` with sane timeouts, a modern TLS floor, graceful shutdown that waits for in-flight requests, and a health/readiness/liveness triple that actually probes the dependencies it claims to check rather than always returning `200`. The liveness/readiness split matters operationally: **liveness** answers "is this process wedged and should the orchestrator restart it" — it must never depend on anything external, or a database outage causes a restart storm across every pod; **readiness** answers "should the load balancer send this pod traffic right now" — it must depend on exactly the things a request needs to succeed. Conflating the two is the single most common Kubernetes health-check mistake; this package keeps them as separate handlers backed by separate check sets on purpose.

## What is observable today

| Signal | Mechanism |
|---|---|
| Request tracing | OpenTelemetry spans, rendered to structured `slog` (no live OTLP exporter wired) |
| HTTP metrics | Prometheus, exposed at `/metrics` |
| Application logs | Structured `slog`, correlated with trace id |
| Audit trail | `internal/domain/audit`, queryable via `GET /audit`, verifiable via `GET /audit/verify` |
| Discovery run health | Per-(service, region) job status, denied-actions list, `APICalls`/`Throttled` counters (`ports.DiscoveryOutput`) |
| LLM call health | Latency and token metrics via `internal/adapters/llm/middleware` |
| Execution plan health | Per-step status, retry count, via `execute.Plan`'s persisted state |

## Current limitations

- No live OTLP exporter is wired; trace data is only as good as `slog`-formatted spans until one is added.
- No dashboard (Grafana or otherwise) has been built against the exposed Prometheus metrics in this codebase — the metrics exist; a reference dashboard does not.
- No alertmanager/PagerDuty integration exists; `docs/slos.md`'s alerting section describes intended alert conditions, not wired alerting rules.
- Telemetry has never observed real production traffic — every metric and trace so far has been generated by unit/integration tests and the demo tenant.
