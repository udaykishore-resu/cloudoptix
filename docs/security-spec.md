# Security specification

Covers `SPEC-SEC-001..005`. See the root README's [Security model](../README.md#security-model) for the summary table; this document is the detailed specification.

## SPEC-SEC-001 — AssumeRole-only AWS access

`internal/adapters/aws/sts` is CloudOptix's only path onto a customer's AWS account, and the design is structural, not procedural: the package has no function, constructor option, or struct field anywhere that accepts an AWS access key ID or secret access key. `Broker` is built from an `aws.Config` whose `Credentials` this package never sets from a literal — the caller supplies a base config from however its own runtime provides identity (an ECS task role, an EC2 instance profile, a local SSO profile in development), and every credential this package hands back afterward is minted by `sts:AssumeRole` against that base identity, never accepted as input. A reviewer can verify "no static keys ever touch a customer account" by grepping the package for `AccessKeyId`/`SecretAccessKey` as an input parameter and finding none — it is not a policy CloudOptix promises to follow, it is a shape the code cannot express.

**Four IAM role scopes, four separate roles** (`cloud.RoleScope`): `read` (`Describe*/List*/Get*` on inventory), `analyze` (CloudWatch, Cost Explorer, CUR), `plan` (dry-run/simulate APIs only), `execute` (the narrow mutating set, per action type). These are distinct roles a tenant creates in their own account, not four permission checks against one wide role — a tenant that never creates the execute role simply has no way to obtain an execute-scoped session; `Broker.Assume` returns an error the same way a real `AssumeRole` against a nonexistent role would.

**The confused-deputy defence.** Every `AssumeRole` call carries the account's `ExternalID` — generated by CloudOptix, unique per account, required in the customer's trust policy — so a customer's trust policy cannot be assumed by any CloudOptix tenant, only the one it was written for. `RoleSessionName` is built from the CloudOptix principal and the requesting scope, so the customer's own CloudTrail attributes every action CloudOptix took to a specific session, never an anonymous `AssumeRole` line.

**Session caching and coalescing.** Sessions are cached per (account, scope) and refreshed proactively — a caller never observes an about-to-expire credential. Concurrent refreshes for the same key coalesce onto one `AssumeRole` call rather than stampeding STS when many goroutines discover the same expired session at once: `Broker.Assume` serializes refresh through a per-key mutex, and the `aws.CredentialsCache` wrapping every minted session's provider adds a second layer of coalescing at the point credentials are actually used to sign a request.

**Connection verification, not blind trust.** `POST /aws-accounts/{id}/verify` drives an `AssumeRole` probe recording `GrantedScopes` and `MissingActions` per role; `ConnectionState` moves through `pending → verifying → connected | degraded | failed`. `degraded` means connected but missing optional permissions — the tenant is told exactly which actions are missing, not left to guess from a partial discovery result.

## SPEC-SEC-002 — RBAC

Nine roles (`core.Role`), permissions resolved by table lookup (`rolePermissions`, `internal/domain/core/principal.go`), never stored per-user, so a policy change applies immediately and uniformly. See the root README's [RBAC table](../README.md#security-model) for the full role-by-capability breakdown. Two properties matter most:

- `RoleAuditor` can read everything, including the audit log, but change nothing at all — credentials stolen from an auditor cannot move money.
- `RolePlatformAdmin` is explicitly carved out of `PermExecutionStart`/`PermRollbackStart` in `Principal.Can`: CloudOptix's own operators can read a tenant's data for support but cannot themselves push a tenant's infrastructure change — that has to come from the tenant.

Every route names exactly one `core.Permission` in the declarative table (`internal/transport/http/routes.go`), tested (`rbac_test.go`) to assert every mutating route carries one. Handlers re-check the identical permission via `core.Principal.Authorize` before touching a service, independent of the router's own enforcement, so a handler reachable by a path the router doesn't know about still fails closed.

## SPEC-SEC-003 — Tenant isolation, structural at every layer

`core.TenantID` is a distinct type — not a bare string — carried by every repository method, cache key, and event; the compiler is the cheapest place to catch a missing or swapped tenant scope. `core.GuardTenant` is structural inside every `memstore` repository method (`internal/adapters/memstore/doc.go`), not a convention call sites are trusted to apply. `ports.KnowledgeStore.Search` (the RAG store) has no tenant-filter parameter to omit at all — every query is structurally intersected with (platform-wide documents) ∪ (the querying tenant's own documents) before ranking runs, because there is no filter argument to forget. `internal/transport/http/tenant_isolation_test.go` exercises this at the HTTP layer directly.

## SPEC-SEC-004 — Authentication and the AI sanitization boundary

`internal/infrastructure/auth` turns an inbound bearer token into a `core.Principal` scoped to one tenant, accepting three structurally distinct token shapes rather than funnelling everything through one lenient parser:

| Token shape | Path | Notes |
|---|---|---|
| OIDC-issued JWT | Every human user | Validated against a JWKS fetched, cached, and rotated from the tenant's identity provider |
| Service token | Discovery/execution/notification workers, acting as `core.SystemPrincipal` | An HS256 JWT signed with a platform-held HMAC secret — deliberately a *different signing method* from the OIDC path, so a worker credential can never be replayed as a user credential or vice versa |
| Development static token | Local iteration with no identity provider running | `NewDevIssuer` refuses to construct when told the environment is production — this path cannot reach a real deployment by a config mistake alone |

**Algorithm-confusion defence.** The JWT parser's algorithm allowlist is explicit and closed (`jwt.WithValidMethods`); `"none"` is never in it, and the asymmetric (OIDC) and symmetric (service-token) paths never share a `Keyfunc`. This is what actually prevents algorithm confusion — an attacker crafting an HS256 token and "signing" it with the server's public RSA key, which a single Keyfunc returning either key type depending on the token's own claimed algorithm would otherwise accept as a valid HMAC secret. A single shared Keyfunc is the classic way this vulnerability gets reintroduced; this package never does that.

`SPEC-SEC-004` is also cited (from `middleware/doc.go`) for the AI input/output sanitization boundary — see [`ai-spec.md`](ai-spec.md)'s `SPEC-AI-002` section for the full detail: prompt-injection defence on every tool result and retrieved document, applied in middleware so it cannot be skipped by a call site that forgot.

## SPEC-SEC-005 — Audit

`internal/domain/audit`: records are **hash-chained** — each stores the SHA-256 hash of its predecessor for the same tenant (`Record.ComputeHash`, `Record.Seal`), so removing or editing a record breaks the chain at every subsequent entry, detectable in one verification pass (`audit.VerifyChain`, exposed via `GET /audit/verify`). This does not make the log immutable — nothing stored in a mutable database is — but it makes tampering detectable with a single check, which is the property an auditor actually needs; production deployments additionally write records to object storage under a retention lock for true immutability. `Action` is a closed, enumerated vocabulary (`tenant.created`, `spec.approved`, `aws.assume_role`, `slo.breached`, `recommendation.created`, ...) so a query for "every production execution last quarter" is exact, never a text search.

## Current limitations

- No penetration test, dependency audit, or third-party security review has been performed on this codebase. Every mitigation described above is a real, structural defence for a specifically named attack (confused deputy, algorithm confusion, tenant-scope omission, audit tampering) — not a substitute for an actual review, which has not happened.
- `internal/adapters/aws/sts` is unit-tested (`broker_test.go`, `verify_test.go`) against mocked STS responses; it has never assumed a role in a real AWS account.
- Secrets management is a `SecretRef` indirection (`ports.SecretResolver`) with no reference AWS Secrets Manager or Vault-backed implementation built or tested in this environment — every notify channel and CUR credential resolves through an interface with no production-grade implementation present.
- `internal/domain/audit`'s hash-chain logic has no dedicated `_test.go` file of its own — it is exercised indirectly through `internal/adapters/memstore/audit_test.go`. The production object-storage-with-retention-lock write path described above is a documented design intent, not an implemented adapter in this codebase.
