# cloudoptix-onboarding-role

**This is the module you, the customer, run in your own AWS account to
connect it to CloudOptix.** It creates up to four IAM roles — nothing else —
that CloudOptix assumes via `sts:AssumeRole` to inventory, analyze, plan
against, and (only if you grant it) change resources in this account.

If your organization launches infrastructure via CloudFormation instead of
Terraform, `cloudformation.yaml` in this directory is the equivalent
one-click stack — same four roles, same trust policy, same action lists,
kept in sync by hand (see that file's header comment).

## What this does NOT do

This module does not touch any resource other than the four IAM roles and
their inline policies. It does not create a VPC, a CloudTrail trail, or
anything billable. It grants CloudOptix nothing until you run `terraform
apply` — reviewing the plan output before applying is the right way to
verify this module matches what is described below before it takes effect.

## The trust policy — how CloudOptix actually gets in

Every role's trust policy is exactly:

```json
{
  "Effect": "Allow",
  "Principal": { "AWS": "<cloudoptix_principal_arn>" },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": { "sts:ExternalId": "<external_id>" }
  }
}
```

`external_id` is generated by CloudOptix, once, specifically for your
account (`internal/application/onboarding/iam.go`'s `generateExternalID` —
a 32-character random hex string, always prefixed `cloudoptix-`) and shown
to you once on the onboarding screen. The `StringEquals` condition on
`sts:ExternalId` is the standard AWS defence against the [confused deputy
problem](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-user_externalid.html):
without it, if CloudOptix's own AWS account ID were ever guessed or leaked,
anyone who knew it could ask CloudOptix's systems to assume a role in *your*
account, because the trust policy alone (principal only, no external ID)
cannot distinguish "the real CloudOptix, acting on your behalf" from
"someone who found CloudOptix's account ID." Never approve a change that
removes this condition or accepts a wildcard external ID.

`internal/adapters/aws/sts/broker.go` is the code that actually calls
`AssumeRole` against these roles at runtime — every session it mints is
named `cloudoptix-<principal>-<account>-<scope>` (visible in your
CloudTrail as the `RoleSessionName`), which is how you can attribute a
specific API call in your CloudTrail back to a specific CloudOptix
component and account, not just to "someone assumed this role."

## The four roles, and why each action is on its list

Every action list below is copied verbatim from
`internal/application/onboarding/iam.go` — the same Go source the
CloudOptix product itself uses to render these exact policies on your
onboarding screen. This README is not a paraphrase of what CloudOptix does;
it is a description of the literal code path, cross-referenced so you can
verify it yourself.

### `CloudOptix-<tenant>-Read`

Everything CloudOptix's discovery scanners
(`internal/adapters/aws/discovery/`) call to build an inventory of your
estate. Every action is a `Describe*`/`List*`/`Get*` read — nothing here
can modify a resource.

| Action(s) | Why |
|---|---|
| `ec2:Describe*` | Instances, volumes, snapshots, AMIs, Elastic IPs, VPCs, subnets, security groups, NAT gateways, VPC endpoints, transit gateway attachments — see `internal/adapters/aws/discovery/ec2.go`'s `RequiredActions()`. |
| `rds:Describe*`, `rds:ListTagsForResource` | RDS/Aurora instances, clusters and snapshots (`discovery/rds.go`), plus the security groups they're attached to (covered by `ec2:Describe*` above). |
| `s3:ListAllMyBuckets`, `s3:GetBucketLocation`, `s3:GetBucketTagging`, `s3:GetBucketLifecycleConfiguration` | Enumerate buckets and their existing lifecycle configuration — the exact input the `apply_s3_lifecycle` recommendation needs to know whether one is already in place (`discovery/s3.go`). |
| `lambda:List*`, `lambda:GetFunction*` | Functions, their configuration, tags, and provisioned-concurrency configs (`discovery/lambda.go`). |
| `ecs:Describe*`, `ecs:List*` | Clusters, services, task definitions (`discovery/ecs.go`). |
| `eks:Describe*`, `eks:List*` | Clusters and node groups (`discovery/eks.go`). |
| `elasticloadbalancing:Describe*` | Load balancers, target groups, target health, tags (`discovery/elbv2.go`). |
| `autoscaling:Describe*` | Auto Scaling groups (`discovery/asg.go`). |
| `dynamodb:Describe*`, `dynamodb:List*` | Tables and their tags (`discovery/dynamodb.go`). |
| `elasticache:Describe*` | Cache clusters and their tags (`discovery/elasticache.go`). |
| `tag:GetResources`, `tag:GetTagKeys`, `tag:GetTagValues` | Cross-service tag-based resource discovery and cost-allocation tag enrichment (`discovery/resourcegroupstagging.go`). |
| `organizations:ListAccounts`, `organizations:DescribeOrganization` | Only meaningful if you connect an AWS Organizations management account; lets CloudOptix enumerate member accounts for org-wide onboarding rather than you registering each one by hand. |

Not listed above but present in individual discoverers and covered by the
same `Describe*` wildcards: `secretsmanager:ListSecrets` (existence and
metadata only — CloudOptix never reads a secret's value),
`cloudfront:ListDistributions`/`ListTagsForResource`,
`events:ListEventBuses`/`ListRules`/`ListTagsForResource`,
`sns:ListTopics`/`GetTopicAttributes`/`ListTagsForResource`,
`sqs:ListQueues`/`GetQueueAttributes`/`ListQueueTags`,
`kms:ListKeys`/`DescribeKey`/`ListResourceTags`, `apigateway:GET`. These are
each individually narrow (see the corresponding file in
`internal/adapters/aws/discovery/`) and are folded into the tenant's
resource-groups-tagging-driven discovery pass rather than each getting a
dedicated top-level bullet here.

### `CloudOptix-<tenant>-Analyze`

Everything **Read** grants, plus:

| Action(s) | Why |
|---|---|
| `ce:GetCostAndUsage`, `ce:GetCostForecast` | The core cost data `internal/application/costing` derives your `cost.*` domain records from. |
| `ce:GetReservationUtilization`, `ce:GetSavingsPlansUtilization`, `ce:GetRightsizingRecommendation` | Commitment coverage/utilization and AWS's own rightsizing signal, cross-referenced against CloudOptix's independent recommendations rather than replacing them. |
| `cur:DescribeReportDefinitions` | Confirms a Cost and Usage Report export exists and where, if you use CUR ingestion (`terraform/modules/storage`'s CUR bucket) rather than the Cost Explorer API alone. |
| `cloudwatch:GetMetricData`, `cloudwatch:GetMetricStatistics`, `cloudwatch:ListMetrics` | Utilization metrics (CPU, memory proxies, connection counts) behind every rightsizing recommendation — this is how CloudOptix tells an *idle* oversized instance from a *busy* one. |
| `pricing:GetProducts`, `pricing:DescribeServices` | The AWS Price List API, used to price a recommendation's before/after cost when the request needs current on-demand pricing beyond what CloudOptix's own embedded pricebook covers. |
| `compute-optimizer:Get*` | Cross-references AWS's own Compute Optimizer findings, when enabled in your account, as an additional signal. |

### `CloudOptix-<tenant>-Plan`

Everything **Read** grants, plus a small, explicitly read-only or
dry-run-only set:

| Action(s) | Why |
|---|---|
| `ec2:DescribeInstanceAttribute` | Additional per-instance detail (e.g. `disableApiTermination`) the plan stage checks before proposing a change. |
| `pricing:GetProducts` | Same as Analyze — pricing a proposed plan's cost delta. |
| `compute-optimizer:GetEC2InstanceRecommendations`, `compute-optimizer:GetRDSDatabaseRecommendations` | Cross-checked against CloudOptix's own plan before it is presented for approval. |

Every mutating AWS API this platform's plan/simulate stage touches (EC2,
RDS) is called **with `DryRun: true`** — the actual mutating call, without
`DryRun`, only ever happens under the **Execute** role, after human or
policy approval. This role cannot change anything even if CloudOptix's own
application logic had a bug that tried.

### `CloudOptix-<tenant>-Execute`

The only role that can change a resource in your account, and the only one
worth reading action-by-action rather than trusting a summary table. Every
entry is scoped to the exact API call the corresponding executor in
`internal/adapters/aws/executor/` makes — see `RequiredActions()` on each
executor for the authoritative, tested list this table is generated from.

| Recommendation type (`optimize.ActionType`) | IAM actions granted | What it does |
|---|---|---|
| `resize_instance` | `ec2:ModifyInstanceAttribute`, `ec2:StopInstances`, `ec2:StartInstances` | Stop → change instance type → start (EC2 requires the instance be stopped to change its type). |
| `stop_instance` | `ec2:StopInstances` | Stop an idle instance. |
| `schedule_shutdown` | `ec2:StopInstances`, `ec2:StartInstances`, `rds:StopDBInstance`, `rds:StartDBInstance` | Off-hours stop/start schedule for EC2 and RDS. |
| `terminate_instance` | `ec2:TerminateInstances` | Permanently remove an instance CloudOptix identified as unused. **Destructive** — CloudOptix's own policy engine (`internal/domain/govern`) never auto-executes this; it always requires human approval, but this IAM action is still required so an approved termination can actually run. |
| `delete_volume` | `ec2:DeleteVolume` | Remove an unattached EBS volume. Destructive; same approval requirement as above. |
| `resize_volume`, `modify_volume_type` | `ec2:ModifyVolume` | Change an EBS volume's size or type (e.g. gp2→gp3) — non-destructive, in-place. |
| `delete_snapshot` | `ec2:DeleteSnapshot` | Remove a stale EBS snapshot. Destructive. |
| `deregister_ami` | `ec2:DeregisterImage`, `ec2:DeleteSnapshot` | Remove an unused custom AMI and its backing snapshot. Destructive. |
| `release_elastic_ip` | `ec2:ReleaseAddress` | Release an unassociated Elastic IP allocation. Destructive (a new allocation gets a different address). |
| `create_vpc_endpoint` | `ec2:CreateVpcEndpoint` | Add an S3 gateway endpoint to remove NAT data-processing charges — the fix `terraform/demo`'s deliberately-NAT-heavy estate is built to need. |
| `remove_nat_gateway` | `ec2:DeleteNatGateway` | Remove a NAT gateway once traffic no longer needs it (typically after `create_vpc_endpoint` has run). |
| `enable_spot` | `autoscaling:UpdateAutoScalingGroup`, `ec2:CreateFleet` | Shift interruption-tolerant capacity onto Spot. |
| `resize_rds` | `rds:ModifyDBInstance` | Change an RDS/Aurora instance class. |
| `modify_rds_storage` | `rds:ModifyDBInstance` | Grow allocated storage (AWS provides no shrink operation, so this is one-directional). |
| `remove_rds_replica` | `rds:DeleteDBInstance` | Remove a read replica with no identified consumer. Destructive. |
| `stop_rds` | `rds:StopDBInstance` | Stop a non-production database outside business hours. |
| `apply_s3_lifecycle` | `s3:PutBucketLifecycleConfiguration` | Add a lifecycle policy (expire old versions, abort stale multipart uploads) to a bucket that has none. |
| `abort_multipart_uploads` | `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`, `s3:ListBucketMultipartUploads` | Clean up abandoned in-progress multipart uploads that are billing you for stored, never-completed parts. |
| `set_log_retention` | `logs:PutRetentionPolicy` | Cap a CloudWatch Logs group's retention instead of the AWS default of "forever." **Granted but not yet callable**: `internal/adapters/aws/executor/logs_unsupported.go` documents this action's required IAM permissions without implementing the executor itself — see that file's doc comment. Nothing in CloudOptix can use this permission today; it is included so the role does not need re-provisioning the day the executor ships. |
| `resize_lambda_memory` | `lambda:UpdateFunctionConfiguration` | Change a function's memory allocation (which also scales its proportional CPU). |
| `switch_lambda_arch` | `lambda:UpdateFunctionConfiguration` | Same call, different parameter — switch between x86_64 and arm64/Graviton. |
| `remove_provisioned_concurrency` | `lambda:DeleteProvisionedConcurrencyConfig` | Remove idle provisioned concurrency you are paying for but not using. |
| `resize_node_group` | `eks:UpdateNodegroupConfig`, `autoscaling:UpdateAutoScalingGroup` | Change an EKS managed node group's min/max/desired size. |
| `adjust_pod_resources` | `eks:DescribeCluster` | Read the cluster endpoint to reach the Kubernetes API directly — the actual pod resource-request change is applied via the cluster's own API (a `kubectl`-equivalent call authenticated through your cluster's own RBAC/IRSA, not an AWS control-plane mutation), which is why this is the only "Execute" action whose IAM grant is a read call. |
| `purchase_commitment` | `ce:GetSavingsPlansPurchaseRecommendation`, `savingsplans:CreateSavingsPlan` | Purchase a Savings Plan CloudOptix recommended. **Financial commitment** — always requires explicit human approval regardless of policy configuration. |
| `switch_dynamo_billing` | `dynamodb:UpdateTable` | Switch a table between on-demand and provisioned billing mode. |

**On "destructive" actions still being IAM-granted here**: CloudOptix's own
policy engine (`internal/domain/govern.Policy`) is what decides whether a
given recommendation type can auto-execute, requires human approval, or is
prohibited outright — that decision is made in the application, per your
own configured policy, every single time, regardless of what this IAM role
permits. This role's job is narrower: once your policy (or a human) has
approved a specific action, this is what makes it *possible* for CloudOptix
to carry it out. An IAM role that omitted `ec2:TerminateInstances` would
not make CloudOptix's termination recommendations any safer — it would
just mean an approved termination fails with `AccessDenied` instead of
succeeding, which is a worse failure mode for an approval workflow you
already trusted.

## `enabled_scopes`: grant only what you're ready for

You do not have to grant all four roles at once. A common rollout is:
connect with `read` only for the first few weeks (inventory and dashboards,
zero write access exists in the account at all), add `analyze`/`plan` once
you trust the recommendations, and add `execute` only once you are ready
for approved changes to actually apply. Set `enabled_scopes` to whichever
subset you want; re-running `terraform apply` with a larger set later adds
the missing roles without touching the ones that already exist.

## Reviewing before you apply

- `terraform plan` shows you the exact IAM policy documents this module
  will create — read it, not just this README.
- Every action list here has `Resource: "*"` — CloudOptix does not know
  your resource ARNs until discovery (which runs under the `Read` role)
  has found them, so the boundary is entirely in the **action list**, not a
  resource constraint. This is normal for an inventory/cost-management
  tool's initial connection; it is not a sign the policy is broader than it
  needs to be.
- If your organization requires an IAM permissions boundary on every role,
  set `permissions_boundary_arn`.
